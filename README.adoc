== YubiHSM 2.7.2 opaque

This is a modified version of the YubiHSM Shell 2.7.2 that accepts values other than 'Opaque object' for the CKA_APPLICATION attribute of CKO_DATA objects.

=== Root Cause Analysis

There are two separate bugs that together cause your observation: one at write time and one at read time.

==== Bug 1 — C_CreateObject silently discards CKA_APPLICATION

In yubihsm_pkcs11.c, the CKO_DATA branch of C_CreateObject lists CKA_APPLICATION in its switch statement but does nothing with it — it just breaks:

```
case CKA_TOKEN:
case CKA_CLASS:
case CKA_ID:
case CKA_LABEL:
case CKA_APPLICATION:   // <-- silently accepted, value never saved
case CKA_OBJECT_ID:
case CKA_SUBJECT:
...
  break;
```

The value you pass in is thrown away before the yh_util_import_opaque_ex call is ever made.

==== Bug 2 — get_attribute_opaque always returns a hardcoded string

In util_pkcs11.c, inside get_attribute_opaque, the CKA_APPLICATION case is hardcoded unconditionally:

~~~
case CKA_APPLICATION: {
  char *str = "Opaque object";
  strcpy((char *) value, str);
  *length = strlen(str);
} break;
~~~

There is no mechanism to read back anything else. Even if you had managed to persist the value somewhere, this code would always overwrite the response.

=== Why There Is No Easy Storage Slot

The YubiHSM 2 firmware YH_OPAQUE object has a fixed schema: id, label, domains, capabilities, algorithm, and value. There is no native application field. The library already solves the analogous problem for CKA_ID and CKA_LABEL on asymmetric/certificate objects using a meta object — a second YH_OPAQUE object stored alongside the target object whose value carries TLV-encoded PKCS#11 metadata. You need to extend that system.

=== Required Changes

==== 1. Add cka_application to pkcs11_meta_object in yubihsm_pkcs11.h

~~~
typedef struct {
  uint16_t target_id;
  yh_object_type target_type;
  uint8_t target_sequence;
  cka_meta_item cka_id;
  cka_meta_item cka_label;
  cka_meta_item cka_id_pubkey;
  cka_meta_item cka_label_pubkey;
  cka_meta_item cka_application;   // <-- add this
} pkcs11_meta_object;
~~~

==== 2. Add a new TLV tag constant in util_pkcs11.c

Near the existing tag definitions:

~~~
#define PKCS11_ID_TAG          1
#define PKCS11_LABEL_TAG       2
#define PKCS11_PUBKEY_ID_TAG   3
#define PKCS11_PUBKEY_LABEL_TAG 4
#define PKCS11_APPLICATION_TAG  5   // <-- add this
~~~

==== 3. Wire the tag into write_meta_object and read_meta_object in util_pkcs11.c

In write_meta_object, add to both the length calculation and the serialization:

~~~
// Length calculation — add this alongside the existing cka_label_pubkey term:
+ (meta_object->cka_application.len == 0
       ? 0
       : 3 + meta_object->cka_application.len)

// Serialization — add after the existing write_meta_item calls:
p += write_meta_item(p, PKCS11_APPLICATION_TAG, &meta_object->cka_application);
~~~

In read_meta_object, add a case to the TLV parsing loop:

~~~
case PKCS11_APPLICATION_TAG:
    len = read_meta_item(p, &meta_object->cka_application);
    break;
~~~

==== 4. Parse and store CKA_APPLICATION in C_CreateObject in yubihsm_pkcs11.c

Add a pkcs11_meta_object local for the CKO_DATA branch (it already exists as meta_object in that scope). Change the silent break for CKA_APPLICATION into actual parsing:

~~~
case CKA_APPLICATION:
    if (pTemplate[i].ulValueLen > CKA_ATTRIBUTE_VALUE_SIZE) {
        DBG_ERR("CKA_APPLICATION value too large");
        rv = CKR_ATTRIBUTE_VALUE_INVALID;
        goto c_co_out;
    }
    meta_object.cka_application.len = pTemplate[i].ulValueLen;
    memcpy(meta_object.cka_application.value,
           pTemplate[i].pValue,
           pTemplate[i].ulValueLen);
    break;
~~~

Then, after the yh_util_import_opaque_ex call succeeds, trigger meta-object creation for CKO_DATA when cka_application is set (the existing code only triggers for CKO_CERTIFICATE). Extend the condition:

~~~
// Was:
if (algo == YH_ALGO_OPAQUE_X509_CERTIFICATE &&
    (meta_object.cka_id.len > 0 || meta_object.cka_label.len > 0)) {
    meta_object.target_id = template.id;
}

// Change to:
if ((meta_object.cka_id.len > 0 ||
     meta_object.cka_label.len > 0 ||
     meta_object.cka_application.len > 0) &&
    (algo == YH_ALGO_OPAQUE_X509_CERTIFICATE ||
     algo == YH_ALGO_OPAQUE_DATA)) {
    meta_object.target_id = template.id;
}
~~~

==== 5. Fix get_attribute_opaque in util_pkcs11.c to read back the stored value

The function already receives a meta_object pointer. Change the hardcoded case:

~~~
case CKA_APPLICATION: {
    if (meta_object != NULL && meta_object->cka_application.len > 0) {
        if (*length < meta_object->cka_application.len) {
            return CKR_HOST_MEMORY;
        }
        *length = meta_object->cka_application.len;
        memcpy(value,
               meta_object->cka_application.value,
               meta_object->cka_application.len);
    } else {
        // Preserve original fallback for objects created without the attribute
        char *str = "Opaque object";
        strcpy((char *) value, str);
        *length = strlen(str);
    }
} break;
~~~

=== How It All Fits Together at Runtime

After these changes, the flow becomes:

1. C_CreateObject — parses CKA_APPLICATION into meta_object.cka_application, then calls write_meta_object which serializes it as a TLV tag 5 blob into a companion YH_OPAQUE object on the device, labelled "Meta object for 0x<seq><type><id>".

2. Login / populate_cache_with_data_opaques — loads all YH_ALGO_OPAQUE_DATA objects including both the data object and its meta companion into the slot cache. _get_object_desc detects the meta object via is_meta_object and calls read_meta_object, which deserializes TLV tag 5 back into meta_object.cka_application.

3. C_GetAttributeValue → get_attribute_opaque — find_meta_object_by_target locates the companion in cache; get_attribute_opaque reads meta_object->cka_application and returns your stored string instead of the hardcoded one.

One thing to be aware of: the find_meta_object_by_target call in get_attribute matches on target_domains. Make sure the authentication key used has domain access that overlaps with the domain the opaque object was stored in, which is already a requirement for the existing meta-object machinery.


== YubiHSM Shell

This repository contains most of the components used to interact with
the YubiHSM 2 at both a user-facing and programmatic level.

The available components are:

- link:lib/README.adoc[libyubihsm] -- C library to expose low- and high-level functions to
  interact with a YubiHSM

- link:src/README.adoc[yubihsm-shell] -- thin wrapper around `libyubihsm` providing both
  an interactive and command-line interface to a YubiHSM

- link:pkcs11/README.adoc[yubihsm-pkcs11] -- PKCS#11 module using `libyubihsm`

- link:yhwrap/README.adoc[yubihsm-wrap] -- command-line tool to create encrypted objects (wraps) that can be imported in the YubiHSM

- link:ykhsmauth/README.adoc[libykhsmauth] -- C library for using the YubiKey HSM Auth application

- link:yubihsm-auth/README.adoc[yubihsm-auth] -- command-line tool to use the YubiKey HSM Auth application

Documentation for this project and the YubiHSM2 in general can be found on Yubico's https://developers.yubico.com/YubiHSM2/[developers website].

=== pre-commit

This repository uses https://pre-commit.com/[pre-commit].

 $ pre-commit install

=== Building

 $ mkdir build && cd build
 $ cmake ..
 $ make

Note that `ninja` builds are available as well:

 $ mkdir build && cd build
 $ cmake -GNinja ..
 $ ninja

The binaries will be located in `build` directory. To install them on the system, run the following command. Note that this
step may require admin privileges on some systems (e.g. `sudo` on Linux)

 $ make install

IMPORTANT: Building from source on Windows should be made with the source from the source release package and not
directly from the cloned repository. This is due to the `gengetopt` library not being available for Windows.

Manpages are built by default using `help2man`. It is possible to skip this step with:

 $ mkdir build && cd build
 $ cmake -DWITHOUT_MANPAGES=1 ..
 $ make

It is possible to build the libraries and binaries with static linking, this can be enabled with:

  $ mkdir build && cd build
  $ cmake -DENABLE_STATIC=1 ..
  $ make

=== Linting

There is a `cppcheck` target that runs the source through `cppcheck`

 $ make cppcheck

=== Testing

PKCS#11 tests can be run using https://github.com/Yubico/pkcs11test[pkcs11test].

The tool must be already built, and the path to the resulting binary
must be in your `PATH`, or `PKCS11TEST_PATH` must be set.

The programs found in the `/examples` directory are also used as tests.

The tests can be run via

 $ make test

Or using ctest directly

 $ ctest

By default the tests expect a local connector running at `http://localhost:12345`.
A different connector for the tests can be specified by setting the
`DEFAULT_CONNECTOR_URL` environment variable.
For example, to run tests using direct USB (i.e., without a connector) use

 $ DEFAULT_CONNECTOR_URL="yhusb://" ctest

If you are building `yubihsm-shell` with `ninja`, the following is available:

 $ ninja test

The test output can be found in `.../yubihsm-shell/build/Testing/Temporary/LastTest{,sFailed}.log`.

Direct command-line output can be obtained with

 $ ctest -V

==== Coverage

Code coverage is provided courtesy of lcov and https://github.com/RWTH-HPC/CMake-codecov[CMake-codecov]. This currently only works with `make` and not with `ninja`.

Enable coverage with

 $ cmake -DENABLE_COVERAGE=1 ..

You can then build the project normally and run some executables (for example running the tests with `make test`).

At this point coverage evaluation can be generated with gcov/lcov related targets. For example

 $ make lcov

will generate a single HTML report in `./lcov/html/all_targets/index.html`
